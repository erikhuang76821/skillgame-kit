## 1. 問題的來源：四層混在一起

| 層 | 內容 | 例子 | 通用程度 |
|---|---|---|---|
| 契約 | 輕量 skill game 的定義 | 同種子同輸入得同結果、可重播驗分、包體上限、不從 CDN 載入、排除機率玩法 | 通用 |
| 問題 | 每款都要回答的事 | 技巧是否決定結果、難度是否合理、簡單打法離上限多遠 | 通用 |
| 量法 | 怎麼量 | 種子 × 分級 bot、逐段難度指數、人性化 bot 的清怪率 | 依遊戲結構 |
| 門檻 | 量出來要多少 | 各條規則的數值 | 只有 1–3 款的證據 |

現在的規則常把後三層綁成一條，節點的產出與測試卡又把量法寫成檔名。修正方向是分開標示，各自有適用範圍。這個模型是討論中的整理，尚未被任何決策採用。

## 2. 現況盤點

### 可以用的

| 部分 | 現況 |
|---|---|
| 規則 | 集中在 `index/rules.json`，是數字的唯一來源；把關程式都從這裡取值 |
| 知識庫 | 每個 H2 一張卡，有 facet 標記與自動產生的索引 |
| 測試庫 | 每條規則都有對應的測試卡 |
| 資產庫 | 各遊戲登錄後彙整成中央索引 |
| 動態索引 | `context.mjs` 依節點與遊戲 profile 取出規則、知識、測試、資產 |
| 迴圈 | N0–N11；`loop.mjs` 的 status／next／gate／log；進度由紀錄檔重建；人工核准綁定檔案內容 |
| 把關 | pre-commit 跑 shared 測試、碰到的遊戲的測試與 audit、索引檢查 |

紙上試跑確認：階段順序、契約層、精髓七條與去隨機化的內容，對非動作類題目仍成立。

| # | 問題 | 決定 | 含意 |

## 9. 不要做的事

- 不把單一遊戲量到的數字寫成跨遊戲的門檻。
- 不把討論中引用、未查證的判例或「業界判準」寫進知識庫。
- 不為還沒有人要做的遊戲形態預先建系統；用紙上試跑的故障清單決定要補什麼。

## 10. 執行紀錄

### 步驟 1：適用範圍與關卡漏洞（2026-11-11）

方案經 Codex 與 Gemini 兩輪討論後修正：補上「資料待補」怎麼傳到關卡、只有必過規則待補才擋關、先判明確不符再判缺值、三種結果也套用到既有的品類／渲染方式／來源。

| 項目 | 做了什麼 |
|---|---|
| profile | 新增布林欄位 `scriptedProgression`（同一局內是否有可量測的預設段落）；不是檢索用的 facet。三款既有遊戲都填 `true`：GateLane 有波次腳本、TwinStrike 有段落譜面、SwarmDuel 有敵潮時間表 |
| 規則 | 五條難度曲線規則的適用範圍從沒人檢查的 `difficulty` 改成 `scriptedProgression`；門檻不動 |
| 取用器 | 規則的適用判斷改成三種結果：適用、不適用、資料待補。待補的規則不進脈絡包，另列清單（規則、層級、缺哪個欄位） |
| 關卡 | 取用器有錯誤，或關卡要求的必過規則資料待補 → 結果是「無法驗證」。should 層級的待補只列出、不擋關 |
| 索引建置 | 規則的適用範圍只能用認得的欄位，否則建置失敗 |
| 測試 | 三種結果與優先序、未知欄位、合成 profile 不拿到曲線規則、缺值待補、關卡擋關、三款既有遊戲的規則與測試清單快照（`shared/tools/fixtures/`） |

驗證：三款既有遊戲在 N0–N11 的規則與測試清單前後相同；bootstrap 必讀表沒有變；shared 測試、GateLane 與 TwinStrike 的測試、三款 audit 的結果與改動前相同。

**還沒做到的**：非腳本的遊戲仍會被固定的文件與報告要求擋住（步驟 2）；卡片的缺值比對未改（步驟 6）；實驗資料夾裡的代理 profile 沒有填新欄位，現在重跑會看到曲線規則「資料待補」，和當時保存的輸出不同。

**用乾淨副本驗證時另外發現並修掉的兩個既有錯誤**

### 步驟 3：純步驟的重播（2026-11-11）

**切分改了。** 原訂步驟 3 還包含「節點與測試卡改成證據類型」（C3）。圓桌討論（Codex、Gemini 各兩輪）後取消：

- 節點目前只指名兩張卡（`TEST-UNIT`、`TEST-HUMAN-PLAYTEST`），其餘的卡本來就由規則選出。再加一套證據分類只是幫卡片改名，還多一條平行的軌道。
- `TEST-UNIT` 跑的是整套 `npm test`，標成「確定性證據」會誇大它證明的範圍。
- 那兩張被指名的卡，回合制與解謎遊戲一樣要跑，不需要替換；真正要換的是技巧測試卡，而它卡在步驟 4。

**併入步驟 4 的項目**：遊戲在 profile 指定替代的測試卡；替代卡不繼承原卡實作的規則，只算它自己登記的；替代卡要有可重跑的產出與版本標記，不能只靠結束代碼；遊戲專用的卡放共用登錄並標明屬於哪款；N4 的產出不再寫死 `game/tools/bots.mjs`。

**這一步做了什麼**（只動範本）

| 項目 | 做了什麼 |
|---|---|
| 純步驟重播 | 實測範本現有的重播：完全沒有 tick、只有選擇的遊戲可以錄製、上傳、驗證；改一步、少一步、多一步、調換順序、非法的步都被拒絕。加成 `core.test.mjs` 的正式測試 |
| 選擇數量上限 | 原本沒有上限，純步驟遊戲的 `maxTicks` 是 0，管不到。新增 `GAME.maxChoices`：有 `choose()` 的遊戲必須定義；錄製端到上限就不再接受，重播端在執行前就拒絕超過上限的清單。數字由各遊戲在自己的 sim 定義（比照 `maxTicks`），core 裡沒有數字 |
| 畸形上傳 | 選擇清單不是陣列、項目不是陣列、索引不是整數、log 不是合法字串、種子或 tick 數不是整數：一律判無效，不拋例外 |
| 混合模式 | 補測試：選擇與 tick 交替（物理瞄準類），選擇綁定發生的 tick；選擇未完成時不能推進、世界運作中不能選擇 |
| 範例 | 撞球範例補上 `maxChoices`（等於桿數） |
| 規格範本 | §0、§2、§8 註明回合制寫法、`maxChoices`、「一步一個整數」的編碼要求、悔棋何時進紀錄 |

驗證：範本測試 49 個全過（含審查後補的測試；原有的 golden 不變）；shared 測試全過。

**還沒做到的**

- 三款既有遊戲的 `core/` 是各自的副本，不會自動拿到上限檢查與畸形上傳的防護。
- 「一步一個整數」是目前的最小契約，沒有用真實的牌類或文字遊戲驗證過；通用的步驟格式等有實際需求再定。
- core 還沒拆成通用與即時專用（U7）。

**Codex 審查後的修正（2026-11-11）**

Codex 重現了「畸形上傳一律判無效」當時並不成立，以下都已修正並加測試（測試改成斷言拒絕的原因，不只斷言無效）：

| 問題 | 修正 |
|---|---|
| 超長的 log 會在其他檢查之前先整個解碼；兩百萬字元的填充仍驗證通過 | 驗證改成先做便宜的檢查（形狀、種子、tick 數、選擇數量），log 的長度不得超過宣稱的 tick 數所能產生的上限，超過就不解碼 |
| 上傳內容是 `null` 或不是物件時直接拋例外 | 判無效 |
| log 有多種寫法都能驗過（填充、空的區段、尾端多餘的區段、長度不足） | 只接受錄製端自己的編碼：解碼後重新編碼必須與上傳的字串相同 |
| 種子的別名（負數、超過 32 位元）會重播成另一個種子的局 | 種子必須是 0 到 2³²−1 的整數；tick 數必須在 0 到 `maxTicks` 之間 |
| 選擇清單為 `null` 被當成空清單；選擇項目多帶欄位也能過 | 只有「沒有這個欄位」才當成空清單；每筆選擇必須恰好三欄 |
| 錄得出來不一定驗得過：錄製端接受超過一個位元組的輸入，寫進紀錄的值和 sim 收到的值不同；`choose()` 回傳非布林的真值時兩端都接受 | 錄製端只接受 0–255 的整數；兩端都只認 `choose()` 回傳 `true`。契約註明 `choose()` 回傳 `false` 時不得改動 sim（這點靠文件，程式無法檢查） |
| 規格範本 §1、§2、§7、§8、§9 仍假設每 tick 輸入；悔棋的條件寫得太窄；任意長度文字無法當成一個整數 | 各節補上回合制的寫法；悔棋改成「會改變 sim 狀態就進紀錄」；註明文字輸入要用字表索引或逐字加提交 |
| 規格範本 §12 把技巧佔比的門檻數字寫在文件裡（既有問題） | 改成引用規則編號 |

Codex 另外指出、這一步不處理的：

- 範本的 `main.js` 與 `tools/playtest.mjs` 仍是 tick 驅動。core 支援回合制，不代表整套範本已經能直接做回合制遊戲。
- 日後把新的 core 同步到 TwinStrike 時，它的撞球範例與 `core.test.mjs` 都有 `choose()` 卻沒有 `maxChoices`，要一起補。
- 規格範本 §12「滿局重播耗時」的數字仍寫在文件與範本測試裡，目前沒有對應的規則。
- HTTP 入口要另外限制請求大小；core 只能限制一個大小正常的請求能讓伺服器做多少事。

### 步驟 4a：結果表工具與回合制範例（2026-11-11）

**前提改了。** 使用者說明：repo 裡現有的三款遊戲只是技術上的參考範例，之後進來的輸入很可能是玩法不同的新遊戲。所以步驟 4 的預設路徑為新遊戲設計；「三款結果不變」只當工具的回歸檢查，不再是主要驗收。主要驗收改成：一款非即時動作的遊戲能走完新的技巧證據流程。

步驟 4 拆成五段，各自一個 commit：4a 結果表工具；4b 新規則進 `rules.json`；4c 舊規則限定在現有三款、N4／N5 與測試卡替換；4d N5 的人工核准；4e 知識庫 01 §4 改寫。量法的定案見[技巧證據決策 §9](2026-11-11-skill-evidence.md)。

**4a 做了什麼**（程式全部是範本裡的新增檔案；另外改了範本 `package.json` 的一行指令、skill 說明與兩份決策文件。沒有改現有工具、規則或節點）

| 項目 | 做了什麼 |
|---|---|
| 結果表工具 | `tools/lib/evidence.mjs`：每題每策略的分數、兩兩同題的勝平敗與分差、精確符號檢定、簡單策略的接近程度、Markdown 報告。只需要一組具名策略；不假設 bot 檔名、分級、tick 或秒數。門檻由呼叫端傳入，檔案裡沒有門檻數字；沒傳就只有量測值、沒有判定 |

量到的結果（60 題，調校用批次，只當工具的示範，不是任何玩法結論）：

- 回合制範例：強策略對隨機策略 60 勝 0 平 0 敗；對「拿大的那端」36 勝 24 平 0 敗，簡單策略拿到強策略 92% 的分數。檢定會過，但四成的題目兩者沒有差別、分數也很接近——這正是要交給人判定的情況。
- 即時制示範：強策略對三個對照全勝。隨機策略拿到強策略約 8% 的分數；兩條簡單策略約 1%，幾乎等於不玩，所以「勝過簡單策略」在示範遊戲上沒有鑑別力。示範遊戲的簡單策略留到 4c 換範本預設時處理。（第一版的隨機策略是每個 tick 固定機率亂點，也只有 1%，不符合量法定案，審查後改掉。）

| 策略介面只查表面；出錯時不知道是哪一題 | 依遊戲檢查需要的方法；每一局都跑兩次比對；錯誤訊息帶策略名與題目 |

沒有修的：策略「實際看到什麼」與隨機策略是否真的均勻，工具無法檢查，仍靠人審。不同題數的調校批次與確認批次之間的重疊不在比對範圍內。 確認批次之間可能共用極少數題目，不比對。雜湊的相依檔是文字掃描，掃不到的載入方式要靠人對照報告裡的檔案清單。換一份空的紀錄檔、或事先用程式列出確認題目，工具擋不住；要等 4b–4d 把紀錄檔綁到關卡與人工核准。

**還沒做到的**

- 規則還沒進 `rules.json`，關卡還沒接上（4b–4d）；現有的技巧佔比工具與規則照舊運作。
- 固定題庫（普查）模式、每題重抽、執行雜訊曲線、題目敏感度都還沒實作。
- 名次制、低分制、多人賽不適用目前的判定（工具假設分數越高越好）。
- 沒有用真實的非動作遊戲驗證；回合制範例是為了測工具而做的最小遊戲。
- 確認紀錄只記錄使用，不能證明沒有人先看過題目。
